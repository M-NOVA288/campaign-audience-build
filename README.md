# Campaign Audience Build: HOL26 Holiday Win-Back

An end-to-end database marketing campaign build: selecting a target audience, applying suppressions, de-duplicating, assigning channels, splitting test and control, running QA, and producing vendor-ready files with control totals.

The same logic is written in **SQL** and **SAS**, driven by **Unix shell scripts** the way a campaign operations team typically runs list pulls in production, and rebuilt in **Databricks** (PySpark and Databricks SQL on Delta tables) to show the same pipeline on a modern cloud platform.

> All data is synthetic, generated by `scripts/generate_data.py`. No real customer information is used.

## What it does

```
 raw extracts (CSV)
        │
        ▼
 ┌──────────────────┐   unix/run_campaign.sh
 │ pre-flight checks │   files present, headers, row counts, duplicate keys
 └────────┬─────────┘
          ▼
 ┌──────────────────┐   sql/02  or  sas/02
 │ customer metrics  │   recency, frequency, 24-month net sales
 └────────┬─────────┘
          ▼
 ┌──────────────────┐   sql/03  or  sas/03
 │ audience build    │   eligibility → suppressions → de-dupe → channel
 │                   │   → segment → 10% holdout → cell & offer codes
 └────────┬─────────┘
          ▼
 ┌──────────────────┐   sql/04  or  sas/04
 │ QA gate (10 checks)│  any FAIL stops the job, nothing is released
 └────────┬─────────┘
          ▼
 ┌──────────────────┐   unix/run_campaign.sh + unix/qa_file_checks.sh
 │ vendor files      │   split by channel, holdout kept back,
 │                   │   .ctl with counts + MD5, independent file QA
 └──────────────────┘
```

## Run it

Requires bash and Python 3 (standard library only). Works on Linux and macOS.

```bash
git clone <this repo>
cd campaign-audience-build

python3 scripts/generate_data.py      # create the synthetic data (already included)
unix/run_campaign.sh                  # SQL engine, HOL26, as of 2026-11-01
```

Options:

```bash
unix/run_campaign.sh -c HOL26 -d 2026-11-01 -e sql   # SQL engine (SQLite, runs anywhere)
unix/run_campaign.sh -c HOL26 -d 2026-11-01 -e sas   # SAS batch, if sas is on PATH
```

Output lands in `output/`, logs in `logs/`.

### Running the Databricks version

Runs on **Databricks Free Edition** (free, serverless). No cluster setup or file uploads needed.

1. In Databricks, go to **Workspace → Create → Git folder** and paste this repo's URL.
2. Open `databricks/00_load_raw` and click **Run all**. It creates the `workspace.campaign` schema and loads the CSVs from `data/` into Delta tables.
3. Run `databricks/01_build_audience`. It builds the audience and waterfall, then **reconciles every waterfall step against the SQL engine's committed results** (`output/HOL26_waterfall_20261101.csv`) and stops if any count differs.
4. Run `databricks/02_qa_and_report`. The ten QA checks run in Databricks SQL; any failure stops the notebook with `raise_error()`. The count report follows.

To schedule it, create a Job from `databricks/job_hol26.json` (the Databricks equivalent of `unix/crontab.example`).

How the pieces map across engines:

| Step | SQL | SAS | Databricks |
|---|---|---|---|
| Load extracts | `scripts/load_db.py` | `01_import_raw.sas` | `00_load_raw` (Delta tables) |
| Metrics, waterfall, de-dupe, holdout | `03_build_audience.sql` | `03_build_audience.sas` (PROC SORT + `FIRST.`) | `01_build_audience` (PySpark, `row_number()` window) |
| QA gate | `04_qa_checks.sql` + shell exit | `%qa_gate` → `%abort` | `02_qa_and_report` → `raise_error()` |
| Scheduling | `crontab.example` | `crontab.example` | `job_hol26.json` |

### Running the SAS version

The SAS programs mirror the SQL step for step and produce the same file layout, so the same Unix split and file checks apply. To run them without a server, upload the repo to **SAS OnDemand for Academics** (free), set the project root, and submit the driver:

```sas
options set=PROJECT_ROOT "/home/<your-id>/campaign-audience-build";
%include "/home/<your-id>/campaign-audience-build/sas/run_campaign.sas";
```

## Design choices

- **One drop reason per customer.** Each record is tagged with the first rule that removed it, so the waterfall is a simple count and always reconciles to the starting universe (QA09).
- **Parameters, not hard-coded values.** Dates, windows, thresholds and holdout size are set once in `run_campaign.sh` / `00_config.sas`. A new campaign is a new set of parameters, not a code change.
- **Deterministic holdout.** Control is assigned from a hash of `customer_id`, so a rerun produces the same split and the measurement plan isn't disturbed by a re-pull.
- **Fail closed.** Any QA failure stops the job before files are written. Vendor files are only produced from an audience that passed.
- **Data quality problems are in the data on purpose.** Missing and malformed emails, bad ZIPs, duplicate people, closed accounts and returns are all generated so the rules and QA have something real to handle.
